## 5. How a sale works end to end

1. Buyer opens the landing page and taps Buy. The page calls `POST /api/order` on the Worker (or falls back to the bot link if the Worker URL is unset).
2. The Worker creates an order with a unique memo `PP-XXXXXX` (60-minute expiry) and returns a Keeper/`ton://` pay link for **$2.00 USDT on TON mainnet** (price in USDT, never TON; TON floats). The memo is the order id — the buyer must not edit or delete it.
3. The buyer pays from their wallet, then taps "I paid" in the bot (or waits — the 2-minute cron sweep also checks).
4. The Worker verifies the payment on-chain via TonAPI jetton history (primary; TON Center v2 fallback for native TON): the transaction must match the order's memo **and** amount. Wrong amount / missing memo / wrong network (USDT on TRON/ERC-20 instead of TON) → **never auto-deliver**; the order goes to manual review and the seller resolves it with `/deliver`.
5. On a verified match the Worker tells the bot to deliver: the bot sends the product ZIP via `sendDocument` using the cached `PRODUCT_FILE_ID`. A tx-hash claim recorded before delivery prevents double-delivery; a `paid`-but-undelivered order self-heals on retry / cron sweep.
6. Refunds are manual: the seller sends USDT back from their wallet; the bot only records the refund. There are no chargebacks in crypto.
- **Telegram Stars rule (§6.2 of the Bot Platform Developer Terms):** digital goods in bots/Mini Apps must be sold exclusively in Telegram Stars. Mitigation built into this project: payment happens on the **external landing page only**; the bot is delivery/support only. This is a partial mitigation, not total — state it honestly, do not claim the risk is gone.
